# Стратегія та план рефакторингу (Agro Parts Hub)

Цей документ описує принципи, підходи, патерни та найкращі практики для проведення повного та безпечного рефакторингу вашого проєкту.

## Відповіді на ваші запитання та остаточні рішення

1. **Next.js 16 та кешування**: Ви абсолютно праві! У Next.js 16 з'явилася директива `'use cache'` (Cache Components), яка замінює `unstable_cache`. Ми будемо використовувати саме її на рівні функцій або компонентів для кешування.
2. **Характеристики товарів**: Зрозумів вас. Ми створимо систему обов'язкових характеристик для категорій на рівні БД. Для цього ми додамо таблиці: `attribute` (сутності характеристик, напр. "Діаметр"), `category_attribute` (зв'язок: які характеристики обов'язкові для категорії), та `product_attribute_value` (конкретні значення для товару). Загальний JSONB залишимо лише для неструктурованих/довільних приміток.
3. **Категорії (Багато батьків та гнучкий UX)**: Так, це дуже розповсюджений UX-патерн в e-commerce (фасетна навігація або поліієрархія). Щоб товар міг бути одночасно в "Двигун -> Підшипники" та "Підшипники -> Двигун", ми відмовимося від жорсткого `parentId`. Замість цього використаємо зв'язок Many-to-Many між товарами та категоріями (`product_to_category`), а самі категорії можуть формувати плоский список або теги (або мати дерево через таблицю `category_closure_table`/`category_to_category`).
4. **Zustand vs React Query**: Відмовляємося від обох. Сучасний Next.js (App Router) з Server Components, Server Actions та директивою `'use cache'` дозволяє закрити 99% потреб в управлінні станом та даними без сторонніх бібліотек на клієнті. Стан (наприклад, кошик або фільтри) ми будемо тримати в URL-параметрах або на сервері.
5. **FSD vs Domain-Driven Design (Clean Architecture)**: FSD — це просто адаптація Clean Architecture для фронтенду, але оскільки наш проєкт — це повноцінний фулстек моноліт, ми використаємо класичні принципи **DDD (Domain-Driven Design)** та **Clean Architecture**.

## 1. Архітектурні підходи: DDD та Clean Architecture

Ми поділимо код на чіткі шари, де залежності йдуть лише в одному напрямку (від зовнішніх до внутрішніх). 

### 1.1. Шари (Layers)

1. **Domain Layer (Доменний шар)**: Найглибший шар. Тут знаходяться типи, Zod-схеми та бізнес-правила (наприклад, функція, що вираховує знижку). Не залежить ні від БД, ні від UI.
2. **Infrastructure Layer (Інфраструктура)**: Тут знаходиться Drizzle ORM, Data Access Layer (DAL) (файли із запитами до БД). Тільки цей шар знає про SQL.
3. **Application Layer (Застосунок)**: Server Actions та Сервіси. Цей шар отримує дані з Infrastructure, перевіряє їх через Domain правила і повертає результат.
4. **Presentation Layer (UI)**: React Server Components та Client Components. Вони лише рендерять дані і викликають Server Actions. Ніколи не знають про структуру БД.

### 1.2. Структура тек (Bounded Contexts)
Замість глобальних тек, ми згрупуємо код за "Доменами" (Bounded Contexts):
```text
src/
  modules/                  # або domains/
    catalog/                # Домен: Товари, Категорії, Бренд
      domain/               # Типи, Схеми валідації
      infrastructure/       # Drizzle запити (DAL), 'use cache' функції
      application/          # Server Actions
      presentation/         # UI Компоненти (ProductCard, CategoryList)
    cart/                   # Домен: Кошик, Чекаут
      ...
  app/                      # Next.js роутинг (викликає UI компоненти з modules)
  db/                       # Загальні налаштування підключення та міграції
```

## 2. Найкращі практики для вашого стеку

### 2.1. Next.js 16.3 (App Router)
*   **Директива `'use cache'`**: Використовуватиметься в шарі `infrastructure` для кешування результатів звернень до БД. 
*   **Server Component First**: Усі UI компоненти є серверними за замовчуванням. Клієнтські компоненти (`"use client"`) ізольовані (Leaf Components).
*   **Управління станом**: Повна відмова від Zustand/React Query. Фільтри, пагінація та пошук відбуваються через URL (`searchParams`).

### 2.2. Drizzle ORM та PostgreSQL (Neon)
*   **Гнучкі характеристики (EAV підхід)**: Створення реляційної системи для обов'язкових атрибутів категорії (`attribute`, `category_attribute`, `product_attribute_value`).
*   **Поліієрархія категорій**: Перехід від `parentId` до Many-to-Many (`product_to_category`).

### 2.3. UI / Styling (@base-ui/react + Tailwind)
*   **@base-ui/react**: Залишаємо для складних інтерактивних компонентів (модалки, селекти), щоб зберегти Accessibility (ARIA).
*   **cva + Tailwind**: Залишаємо для типізованих UI компонентів (кнопок, бейджів).

## 3. Покроковий план рефакторингу

Оскільки ми починаємо з бази даних, план виглядає наступним чином:

1.  **Фаза 1: Рефакторинг Бази Даних та Infrastructure Layer (Старт)**
    *   **Крок 1.1**: Оновлення схеми `src/db/schema/store.ts`. Видалення `parentId` з категорій. Створення `product_to_category`, `attribute`, `category_attribute`, `product_attribute_value`.
    *   **Крок 1.2**: Створення структури `src/modules/catalog/infrastructure/`.
    *   **Крок 1.3**: Перенесення всіх прямих `db.select()` з `src/app/` у DAL-функції, з використанням директиви `'use cache'` та `cacheTag`.

2.  **Фаза 2: Рефакторинг Application Layer (Бізнес-логіка)**
    *   Перенесення `src/actions` у відповідні модулі (`src/modules/*/application/`).
    *   Забезпечення використання `revalidateTag` при мутаціях.

3.  **Фаза 3: Рефакторинг Presentation Layer та State**
    *   Видалення Zustand. Переведення всіх клієнтських станів (окрім локального UI) на Server Components + URL `searchParams`.
    *   Стандартизація UI компонентів.
